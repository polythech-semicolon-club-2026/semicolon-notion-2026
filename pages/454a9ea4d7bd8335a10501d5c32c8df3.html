2. [팀원] Clone → 브랜치 생성 → 개인 프로필 페이지 작성 → Commit & Push

목표 : 내 브랜치를 만들고 개인 프로필 HTML을 작성한 뒤 PR을 보낸다.

3. [팀장] PR 확인 → 코드 리뷰 → Approve → Merge

목표 : 팀원들의 PR을 검토하고 main 브랜치에 안전하게 병합한다.

Step 1 — PR 목록 확인

GitHub 레포 → Pull requests 탭
→ 팀원들이 올린 PR 목록 확인

Step 2 — 코드 리뷰 작성

PR 클릭 → Files changed 탭
→ 코드 라인에 마우스 올리면 [+] 버튼 등장
→ [+] 클릭 → 해당 줄에 코멘트 작성 가능

리뷰 예시:
"pages/홍길동.html 경로 잘 연결됐네요! 👍"
"index.html a 태그 href 확인했습니다."

Step 3 — Approve & Merge

1. Review changes 버튼 클릭
2. Approve 선택 → Submit review
3. Merge pull request → Confirm merge
4. Delete branch (브랜치 삭제 권장)
💡 충돌 없는 경우 : 팀원들이 서로 다른 파일(pages/이름.html, css/이름.css)을 만들지만, index.html의 같은 <a href> 줄을 여러 명이 수정하기 때문에 두 번째 PR부터 충돌이 발생합니다. 이게 다음 단계의 핵심!

4. [전원] 상위 브랜치 동기화 — main이 바뀌었을 때 내 브랜치 최신화하기

목표 : 다른 팀원의 PR이 Merge되어 main이 변경됐을 때, 내 브랜치에 최신 main을 반영하는 법을 익힌다.
💡 이게 현업에서 제일 자주 하는 작업입니다!

상황 설명

내가 feature/홍길동 브랜치에서 작업 중
→ 다른 팀원 PR이 Merge되어 main의 index.html이 업데이트됨
→ 내 브랜치의 index.html은 예전 버전 → PR 보내면 충돌 발생
→ 해결: 최신 main을 내 브랜치에 먼저 반영!

Step 1 — main 최신화

# main 브랜치로 이동
git switch main

# 원격 최신 상태 가져오기
git pull origin main

# 커밋 로그 확인 — 다른 팀원 커밋이 보여야 정상
git log --oneline

Step 2 — 내 브랜치로 돌아와서 main 반영

# 내 브랜치로 이동
git switch feature/홍길동

# 최신 main을 내 브랜치에 merge
git merge main

여기서 두 가지 상황이 생겨요

① 충돌 없이 성공하는 경우

# 이런 메시지가 나오면 성공!
# Merge made by the 'ort' strategy.
# 또는
# Already up to date.

# 바로 push 가능
git push origin feature/홍길동

② 에디터가 열리거나 충돌이 발생하는 경우

5. [전원] Merge 에디터 & 충돌 해결 완전 정복

목표 : git merge 시 나타나는 에디터 상황과 충돌 마커를 완전히 이해하고 해결한다.

5-1. Merge Commit 메시지 에디터가 열렸을 때

git merge main 을 실행하면 충돌이 없어도 아래처럼 터미널이 갑자기 다른 화면으로 바뀌는 상황이 생깁니다.

1 Merge branch 'main' into feature/홍길동
2
3 # Please enter the commit message for your merge commit.
4 # Lines starting with '#' are comments.
5 # On branch feature/홍길동
6 # All conflicts have been fixed but you are still merging.
7 ~
8 ~
9 ~
"~/semicolon-git-practice/.git/MERGE_MSG" 7L, 198B

왜 이 화면이 뜨나요?

두 브랜치의 커밋 이력을 합치면서 "이 두 브랜치를 합쳤다"는 기록을 남기는 Merge Commit이 필요할 때, Git이 커밋 메시지를 입력하라고 에디터를 여는 것입니다.

이 화면은 vim (터미널 텍스트 에디터) 입니다. Git의 기본 에디터예요.

해결 방법 — vim에서 나가기

# 방법 1: 메시지 그대로 저장하고 나가기 (가장 많이 씀)
:wq
# : 입력 → w (write, 저장) → q (quit, 종료) → Enter

# 방법 2: 저장 없이 그냥 나가기 (merge 취소하고 싶을 때)
:q!
# : 입력 → q! (강제 종료) → Enter
💡 :wq 가 안 쳐진다면?
vim은 두 가지 모드가 있어요.
- 일반 모드 : 키 입력이 명령어로 인식됨 (:wq 입력 가능한 상태)
- 입력 모드 : 실제 텍스트가 입력됨 (i 키로 진입)
화면에 글자가 이상하게 입력되고 있다면 Esc 키를 먼저 눌러 일반 모드로 돌아온 다음 :wq 를 입력하세요.

vim 기본 명령어 요약

상황입력
일반 모드로 돌아오기Esc
저장하고 나가기:wq • Enter
저장 없이 나가기:q! • Enter
텍스트 입력 모드 진입i

VS Code를 기본 에디터로 설정하면 이 문제가 사라집니다

# Git 기본 에디터를 VS Code로 변경 (한 번만 설정하면 됨)
git config --global core.editor "code --wait"

# 이후 git merge 시 VS Code에서 커밋 메시지 편집창이 열림
# 메시지 확인 후 VS Code 탭을 닫으면 merge 완료

5-2. 스테이징 관련 vim 에디터가 열렸을 때

git add 나 git commit 과정에서도 vim 에디터가 열리는 상황이 있어요.

상황 1 — git commit 메시지 없이 실행했을 때

git commit   # -m 없이 실행하면 vim이 열림
1
2 # Please enter the commit message for your changes. Lines starting
3 # with '#' will be ignored, and an empty message aborts the commit.
4 #
5 # On branch feature/홍길동
6 # Changes to be committed:
7 #       modified:   index.html
8 ~

해결:

# 방법 1: vim에서 직접 메시지 입력
i                          # 입력 모드 진입
feat: 홍길동 링크 추가      # 커밋 메시지 입력
Esc                        # 일반 모드로 복귀
:wq                        # 저장 후 나가기 → 커밋 완료

# 방법 2 (권장): :q! 로 나가고 -m 옵션으로 다시 커밋
:q!                        # 나가기
git commit -m "feat: 홍길동 링크 추가"   # 다시 실행

상황 2 — git add -p (대화형 스테이징) 중 vim이 열렸을 때

git add -p   # 변경사항을 나눠서 스테이징할 때 사용

각 변경사항마다 Stage this hunk? 라고 묻는데, 여기서 e 를 누르면 vim이 열립니다.

# add -p 옵션별 의미
y   # 이 변경사항 스테이징
n   # 이 변경사항 스킵
q   # 종료
e   # vim으로 직접 편집 (잘못 누르면 vim이 열림!)

실수로 e 눌러서 vim이 열렸을 때:

:q!   # 그냥 나가면 됨 (변경사항은 유지됨)

상황 3 — git rebase -i 중 vim이 열렸을 때

git rebase -i HEAD~3   # 최근 3개 커밋 수정

아래처럼 커밋 목록이 vim으로 열려요.

pick abc1234 feat: 헤더 추가
pick def5678 style: 폰트 변경
pick ghi9012 fix: 오타 수정

# Rebase 명령어
# p, pick = 그대로 사용
# r, reword = 커밋 메시지 변경
# d, drop = 커밋 삭제

해결:

# 수정 없이 그냥 나가려면
:q!

# 수정하고 저장하려면
i           # 입력 모드
# pick → squash 등으로 변경
Esc
:wq

5-3. 진짜 충돌(Conflict)이 발생했을 때

git merge main 실행 후 아래 메시지가 나오면 진짜 충돌입니다.

Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.

충돌 상태 확인

git status
# both modified: index.html  ← 이 파일에 충돌이 있음

index.html 안의 충돌 마커

VS Code에서 index.html을 열면 이런 부분이 보입니다.

<<<<<<< HEAD
<a href="pages/홍길동.html" class="profile-btn">프로필 보기 &rarr;</a>
=======
<a href="#" class="profile-btn">프로필 보기 &rarr;</a>
>>>>>>> main

충돌 마커 의미

마커의미
<<<<<<< HEAD여기서부터 내 브랜치(현재)의 내용
=======구분선
>>>>>>> main여기까지 main 브랜치에서 온 내용

VS Code 충돌 해결 UI

VS Code는 충돌 마커 위에 버튼을 자동으로 표시해줍니다.

✅ Accept Current Change   → 내 코드 선택 (HEAD 부분)
✅ Accept Incoming Change  → main에서 온 코드 선택
✅ Accept Both Changes     → 둘 다 남기기
   Compare Changes         → 나란히 비교 보기
💡 이번 실습에서의 올바른 선택

5-4. 자주 나오는 에러 메시지 완전 정리

🔴 CONFLICT (content): Merge conflict in index.html

의미 : index.html의 같은 줄을 두 브랜치에서 다르게 수정함

해결 :

# 1. VS Code에서 충돌 마커 찾아서 해결
# 2. git add index.html
# 3. git commit -m "fix: 충돌 해결"
# 4. git push origin 내브랜치명
🔴 error: Your local changes would be overwritten by merge

의미 : 커밋하지 않은 수정사항이 있는데 merge 시도함

해결 :

# 방법 1: 작업 중인 내용을 임시 저장 후 merge
git stash          # 현재 작업 임시 보관
git merge main     # merge 실행
git stash pop      # 임시 저장 복구

# 방법 2: 일단 커밋하고 merge
git add .
git commit -m "wip: 작업 중 임시 저장"
git merge main
🔴 fatal: Not possible to fast-forward, aborting

의미 : fast-forward merge가 불가능한 상황

해결 :

git merge --no-ff main   # 강제로 merge commit 생성
🔴 Please enter a commit message to explain why this merge is necessary

의미 : Merge commit 메시지 입력이 필요 — vim 에디터가 열린 상태

해결 :

# vim에서 Esc 키 누른 후
:wq
# Enter 키 → merge 완료
🔴 error: failed to push some refs / rejected

의미 : 원격에 내 로컬보다 최신 커밋이 있음 (다른 사람이 이미 push한 경우)

해결 :

git pull origin 내브랜치명   # 원격 최신 상태 먼저 받기
# 충돌 있으면 해결 후
git push origin 내브랜치명
🔴 You have unmerged paths. Fix them up in the work tree, and then use 'git add' to mark resolution

의미 : 충돌 해결은 했지만 아직 git add를 안 한 상태

해결 :

git add .               # 해결된 파일 스테이징
git commit -m "fix: 충돌 해결"
🔴 merge --abort 는 언제 쓰나요?

merge를 시도했다가 취소하고 merge 전 상태로 완전히 돌아가고 싶을 때 사용해요.

git merge --abort   # merge 취소, 원래 상태로 복구

충돌 해결이 너무 복잡하거나, 잘못된 브랜치에 merge를 시도했을 때 유용합니다.

5-5. 전체 흐름 요약

# ── 기본 루틴 (PR 보내기 전 반드시!) ──

git switch main
git pull origin main          # ① 원격 main 최신화

git switch feature/내이름
git merge main                # ② 내 브랜치에 main 반영

# 충돌 없으면 → vim 에디터 열리면 :wq → 완료
# 충돌 있으면 → VS Code에서 마커 해결 → git add → git commit

git push origin feature/내이름   # ③ 원격에 push
# → GitHub PR 페이지에서 Merge 가능 상태 확인
